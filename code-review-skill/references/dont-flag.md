# Don't-Flag List

This list is consulted by **every reviewer** during review and by
**every validator** as a post-score override. A finding that matches a
pattern here is dropped regardless of confidence score.

The purpose of the list is to keep the Fixer focused on correctness
problems that actually affect the shipping code. Most AI code review
failures come from drowning developers in nits and speculative
suggestions; this list is the explicit antidote.

---

## Global patterns (apply to all reviewers)

### CI-enforced concerns
Do not flag:
- Lint violations (ESLint, Prettier, gofmt, rubocop, etc.)
- Type errors that the project's type checker would catch
- Formatting issues (spacing, quote style, line length)
- Import order or grouping

These are caught by existing tooling. If they aren't caught, the fix is
to configure the tooling, not to have an AI reviewer flag them one at
a time.

### Generated and vendored code
Do not flag issues in files that are:
- Under `dist/`, `build/`, `out/`, `.next/`, `__generated__/`, `generated/`
- Named `*.generated.*`, `*.gen.*`, `*.min.js`, `*.bundle.js`
- Inside `node_modules/`, `vendor/`, `third_party/`
- Auto-generated by protoc, codegen tools, or similar

### Test-only intentional violations
Tests often deliberately violate production rules (using `any`,
mocking private methods, hardcoding values, skipping null checks on
test fixtures). Do not flag these unless:
- The violation would cause the test itself to be unreliable (flaky,
  order-dependent, non-deterministic)
- The violation is in production code that happens to be in a test file

### Unprompted test suggestions
Do not flag:
- "Consider adding tests for this"
- "This function has no test coverage"
- "A unit test would be good here"

**Exception**: flag if an R1 standard explicitly requires test coverage
for the kind of change at hand, AND you can quote that standard.

### Unprompted documentation suggestions
Do not flag:
- "This function could use a docstring"
- "Consider adding JSDoc"
- "The README should be updated"

**Exception**: flag if an R1 standard explicitly requires documentation
for the kind of change at hand.

### Vague or speculative findings
Do not flag anything that:
- Says "could be better" without saying what better looks like
- Says "consider X" without concrete evidence X is wrong now
- Speculates about future maintenance difficulty without specifics
- Suggests refactoring unrelated code

Every finding must have concrete evidence and a concrete expected
outcome.

## Role-specific patterns

### R1 (Standards) don't-flag
- Any rule you cannot quote verbatim from a loaded standard file
- Rules from a CLAUDE.md that doesn't scope to the file being flagged
  (CLAUDE.md rules apply only to files at the same path or deeper)
- "Best practices" not explicitly stated in a loaded standard

### R2 (Shallow bugs) don't-flag
- Anything requiring context outside the diff to confirm
- "This variable might be null elsewhere" — that's R3
- "This function might be called concurrently" — that's R3
- Naming suggestions (not bugs)

### R3 (Contextual bugs) don't-flag
- Issues also flagged by R2 (duplicates — R2 wins because shallower context is more robust)
- Issues in code the diff doesn't touch, unless the diff specifically
  breaks assumptions in that code

### R4 (Security) don't-flag
- Pre-existing security posture in unchanged code
- "You should use HTTPS" or other generic hygiene not triggered by
  the diff
- Rate limiting suggestions unless the diff introduces a new public endpoint
- "Consider a security review" — that's what this reviewer is

### R5 (Story) don't-flag
- Code quality issues (not your role)
- "You could also implement Y" if Y isn't in the acceptance criteria
- Scope creep findings above SUGGESTION severity (scope creep is
  often legitimate and not blocking)

---

## Override output format

When a validator drops a finding due to this list, record it:

```json
{
  "finding_number": 12,
  "score": 85,
  "kept": false,
  "override_reason": "don't-flag: unprompted test coverage suggestion"
}
```

The `override_reason` must name which pattern fired, so patterns that
fire often can be reviewed and adjusted.

---

## Adding project-specific don't-flag patterns

If your project has recurring false-positive patterns (e.g., "reviewer
keeps flagging our deliberate use of `any` in the legacy adapter"),
add them to a project-local `REVIEW.md` at the repo root. The standards
discovery stage will pick it up and R1 will pass it to validators as
context.
